Codetective: 날짜 · 신문 · 물건 · 프로필 · 이야기 진행 상태

플레이 확인
- MainScene의 책상 위 신문을 클릭하면 든다. 입력창에 포커스가 없을 때 E로 읽는다.
- 우클릭 / 놓기 버튼은 물건을 원래 자리에 내려놓는다. 읽기 화면에서 ESC는 화면만 닫는다.
- 모니터 입력창, 상담 기록, 프로토콜 편집기 등 모든 InputField의 포커스 중에는 E가 물건을 사용하지 않는다.
- 18:00 이후 HUD 또는 시계 화면의 다음 날 버튼을 누르면 암전 → DAY / 09:00 → 새 신문 순서로 전환된다.
- 기존 Profile 앵글에서 이전/다음 인물로 프로필을 조회한다. 모니터의 인물 선택과 공유된다.
- Kernel 프로필은 말소된 신원으로 시작한다. Thread의 실제 신원은 프로필 목록에 포함하지 않는다.

물건 추가
물건 루트에 HoldableItem과 콜라이더를 둔다. 자식 콜라이더도 지원한다.
Item ID는 고정 식별자, Display Name은 화면 이름, Use는 Newspaper / Profile / Custom이다.
Profile은 Profile ID에 해당 인물의 인스턴스 ID를 지정한다. Custom은 On Use(UnityEvent)를 연결한다.
시작 시 ItemCarryController가 씬의 물건을 등록한다. 나중에 생성한 물건은 game.Carry.Register(item)로 등록한다.
한 번에 한 물건을 든다. 내려놓을 때 원래 부모·위치·회전·크기·콜라이더·물리 상태를 복원한다.
확대된 모니터와 프로필을 읽는 동안에는 든 메시를 숨기고 물건과 사용 버튼은 유지한다.
MainScene / KernelSystems / MorningNewspaperPlacement에서 신문의 가로 위치와 회전을 조절한다.
신문 높이는 책상 렌더러의 윗면에 맞춘다. 현재 종이 모형은 기본 메시이며 읽기 화면은 스크롤을 지원한다.

공유하는 이야기 상태 (Codetective.Operations)
runtime.SetTrigger("facility.archiveSecured", true);   // false로 다시 잠글 수 있음
runtime.GetTrigger("facility.archiveSecured");
runtime.SetQuestStage("nsf.introduction", 20, QuestStatus.Active);
runtime.SetQuestStage("nsf.introduction", 100, QuestStatus.Completed);
runtime.GetQuest("nsf.introduction");                 // 복사본 반환
퀘스트는 고정 ID + 정수 단계 + NotStarted/Active/Completed/Failed 상태다.
StoryCondition은 Triggers On 전부 참, Triggers Off 전부 거짓, Quests의 단계 범위와 상태를 모두 검사한다.
StoryEffects는 같은 ID의 트리거와 퀘스트를 변경한다. 함수·메일·신문이 이 구조를 공유한다.
Facts는 획득한 지식, Authorities는 작전 허가로 유지한다. 가역적인 이야기 상태는 트리거/퀘스트로 관리한다.
진행 상태를 임의로 변경하는 명령은 플레이어 언어에 노출하지 않는다. 스토리/월드 코드가 위 API를 사용한다.

플레이어 공개 범위
Entity Schema / Entity Instance / Field의 Access에서 Player Access와 Story를 설정한다.
함수(ActionDefinition)는 Player Access, Story, Story Effects를 설정한다.
Inherit = 상위 선언(기본 공개), Public = 공개, Internal = 내부용이다.
Internal도 실제 인스턴스에는 남아 있어 월드 코드는 GetValue/SetValue로 사용한다.
공개 멤버의 Story 조건이 맞지 않으면 권한 목록·읽기·쓰기·호출·프로필에서 함께 제한된다.
상위 스키마의 조건은 하위에서도 적용한다. 이름을 직접 입력하거나 기존 참조를 사용해도 우회하지 못한다.
특정 인스턴스만 공개 범위를 바꾸는 API:
entity.SetEntityAccess(PlayerAccess.Internal);
entity.SetVariableAccess("note", PlayerAccess.Public);
entity.SetFunctionAccess("ask", PlayerAccess.Inherit);
공개 범위 변경으로 Story 조건을 무시할 수는 없다. Enabled는 기존처럼 멤버 자체의 활성 상태를 별도로 제어한다.

신문과 메일 제작
Create > Codetective > Story > Newspaper Article / Mail 에셋을 만든다.
ClinicScenario.asset의 Newspaper / Mail 배열에 등록한다.
신문: 고정 ID, Headline, Body, First/Last Day, Priority, Condition, Read Facts, On Read.
아침에 조건을 평가해 그날 기사 ID 목록을 확정한다. 일과 중 상태 변화는 다음 아침의 종이에 반영된다.
이미 발행한 신문은 조건이 바뀌어도 종이 내용이 바뀌지 않는다. On Read는 해당 날짜에 한 번만 실행한다.
메일: Condition으로 도착 여부, On Read / On Accept로 공통 이야기 상태를 변경한다.
샘플: 첫 정부 임무 수락 → nsf.introduction 10 / Active,
후속 보고 완료 → 100 / Completed → 다음 날 InvestigationFollowup 기사.
ResearchFunding 또는 CommunityCare 읽기 → news.nsf_rehabilitation ON
→ 상담손님.재단에대하여() / client.askAboutFoundation() 권한 해금.
현재 기사들은 시스템 확인용 콘텐츠이며 전체 시설/사건 분기를 대신하지 않는다.

저장과 테스트
날짜, 트리거, 퀘스트, 인스턴스 공개 범위, 발행한 신문과 읽음 여부를 KernelSnapshot에 저장한다.
이야기 변경과 날짜 경계는 저장에 반영된다. 구형 저장에는 현재 날짜 신문을 제공한다.
진행 중인 Thread는 잠긴 권한을 실행하기 전에 다시 검사하며, 프로토콜 복사본 테스트는 실제 상태를 바꾸지 않는다.
Core 테스트: StoryProgressionTests, NewspaperTests.
Unity Editor 테스트: ItemCarryTests, TextInputFocusTests, EntityAssetTests.

하루 시작 · 예약 상담 · 업무 정산
Create > Codetective > Story > Clinic Day Plan에서 날짜별 예약 에셋을 만든다.
ClinicScenario.asset / Clinic Days 배열에 등록한다. Day 1 이상은 해당 날짜 전용, Day 0은 전용 일정이 없는 날의 기본 일정이다.
Subtitle은 하루 시작의 큰 DAY 표시 아래에 나온다. 새 게임과 새 날짜에 표시하고 중간 불러오기에는 반복하지 않는다.
첫날 샘플: 09:00 오전 상담 / 11:00 취업 상담 / 14:00 보호자 상담.
Start Minute는 자정 기준 분(09:00=540, 11:00=660, 14:00=840)이다. End Minute=0이면 다음 예약 또는 18:00에 끝난다.
같은 시각의 중복 예약은 거절한다. Condition을 아침에 평가해 오늘의 예약 목록을 확정한다.
Profile ID는 실제 인물 인스턴스 ID를 쓴다. 대사는 해당 프로필로 귀속된다.
Greeting / Farewell / Dialogue와 On Arrival / On Completed / On Time Limit을 에셋에서 설정한다.
clinic.met.<Profile ID>는 첫 방문으로 알게 된 인물, clinic.present.<Profile ID>는 현재 방문 중인 인물이다.
새 인물의 Access / Story에 clinic.met 조건을 지정하면 방문 전 프로필은 숨겨진다.
이전 버전 저장에도 새로 추가된 시나리오 소유 인물은 설치한다. 기존 인물의 저장값과 개인 메모는 유지한다.

입실 → 상담 → 마무리 안내 → 퇴실 순으로 진행한다. 연출 중에는 게임 시계가 멈추고 조작을 잠깐 막는다.
다음 예약 시각에는 진행 중인 상담을 마무리 안내와 함께 종료하고, 퇴실이 완료된 뒤 다음 손님을 들인다.
상담이 비어 있을 때 다음 예약까지 기다리면 Thread 작업과 세계 시간도 진행되며 예약 시각에서 멈춘다.
마지막 손님까지 보낸 후에는 마감까지 기다리기가 표시된다.
MainScene / KernelSystems의 ClinicVisitPresentation에서 Patient Prefab, Entry/Seat/Exit Anchor와 연출 시간을 바꾼다.
현재 기본 인물은 입퇴실 확인용 단순 메시다. Patient Prefab을 연결하면 해당 모델로 대체된다.

18:00에는 마지막 상담의 퇴실을 마친 뒤 업무 정산을 연다. 정산을 닫고 메모를 정리하거나 다음 날을 시작할 수 있다.
상담 결과, 새 데이터, 작성 메모, 읽은 메일, 완료한 Thread 작업과 새 작전 권한을 정리한다.
마감 뒤 추가한 메모는 정산을 다시 열거나 다음 날로 넘어갈 때 반영한다.
입실/상담/마무리/퇴실 단계와 이미 들은 진술, 정산 기준값, 시작 화면 확인 여부를 저장한다.
예약 상담 테스트: ClinicScheduleTests. 시나리오/Unity JSON 연결 테스트: EntityAssetTests.

메일 선택과 예약 문의
Story Mail의 Choices 배열에 고정 ID, 표시 Label, Result(Selected / Approved / Declined)를 지정한다.
Condition, Facts, Authorities, Effects로 각 선택의 공통 이야기 조건과 결과를 연결한다.
Choices가 있는 메일에는 기존 Requires Acceptance를 사용하지 않는다. 기존 임무 메일의 수락 동작은 유지한다.
메일을 읽은 뒤 한 번 답변할 수 있다. 선택한 응답과 표시 이름을 저장하며 같은 답변을 다시 실행해도 효과가 반복되지 않는다.
이미 읽은 메일은 조건이 바뀌어도 수신 내역에 남는다.

예약 문의는 Is Reservation Inquiry를 켜고 Reservation에 Day와 Patient Appointment를 설정한다. 승인 선택지의 Approves Reservation도 켠다.
Unity가 일반 메일에도 비어 있는 Reservation 객체를 만들 수 있으므로 객체의 null 여부로 예약을 판정하지 않는다.
기존 에셋은 Approves Reservation 선택지가 있으면 예약 문의로 인식한다.
승인 선택지는 Result=Approved여야 한다. 거절 선택지는 Result=Declined, Approves Reservation은 끈다.
예약 시각이 지났거나 이미 확정된 예약과 겹치면 승인할 수 없다. 승인 불가 이유는 메일 본문에 표시된다.
End Minute=0인 기존 상담은 다음 확정 예약까지 진행되므로 새 예약이 추가되면 상담 마감 시각도 조정된다.
명시적인 종료 시각이 있는 예약 시간은 보호한다. 거절하거나 답변하지 않은 문의는 확정 일정에 추가하지 않는다.
승인 당일의 예약도 추가할 수 있다. 현재 상담의 대사·진행 상태는 유지하고 다음 손님 시각만 갱신한다.
메일 문의 대사는 기존 Clinic Day Plan 뒤에 등록하므로 새 문의를 추가해도 이전 저장의 대사 위치는 유지한다.

모니터의 스케줄 페이지에서 이전 날 / 오늘 / 다음 날의 확정 예약과 진행 상태를 확인한다.
문의 메일의 스케줄 버튼은 해당 예약 날짜로 이동한다. 스케줄의 문의 메일 버튼은 원문으로 돌아간다.
당일 실제 입실, 상담 종료, 다음 예약까지 기다리기와 마감 정산은 승인한 예약까지 함께 사용한다.
샘플 ClinicReservationInquiry.asset: DAY 2 11:00~12:00 보호자 상담 문의. 승인/거절에 따라 clinic.request.care_followup.* 트리거를 기록한다.
예약 승인·거절·시간 충돌·저장·복사본 격리 테스트: MailReservationTests.

터미널 대화와 첫 작전망 안내
Create > Codetective > Story > Terminal Conversation으로 대화 에셋을 만들고 Scenario의 Terminal Conversations에 등록한다.
MainScene의 ClinicScenario에는 Story/Terminal/KernelOnboarding.asset이 연결되어 있다.
새 게임에서 government-intro 메일을 읽은 뒤 Kernel 페이지로 돌아오면 “Kernel을 찾으셨군요.”로 시작한다.
메일의 임무 수락 여부와 별개로 안내를 받을 수 있다. 실제 업무 시작에는 기존 메일 수락 조건을 유지한다.

Steps의 고정 ID, Lines의 Text/Text Key, Characters Per Second, Pause After로 출력 내용을 작성한다.
Goal은 Help / Allocate / Bind Reference / Invoke / Free / Story Condition / None을 지원한다.
Invoke는 실제 대상 ID와 함수 코드, 인자 수를 판정한다. 한국어·영어 별칭이나 치환 참조를 통한 동작도 인정한다.
동일한 문자열을 그대로 베껴 썼는지를 판정하지 않는다. Story Condition은 기존 트리거·퀘스트 조건을 사용한다.
{slot}은 대화 시작 시 선택한 연습용 치환 이름, {command}는 현재 단계에 맞는 명령 예시다.
Variable Base와 겹치는 기존 데이터·프로토콜·대상 이름이 있으면 다른 연습 이름을 선택한다.
Accept Existing을 켜면 앞서 이미 해둔 등록/연결/해제/함수 수행도 인정한다.

대사가 나오는 동안 명령 입력과 자동완성을 잠근다. 페이지 버튼·스크롤·메뉴는 그대로 사용할 수 있다.
Kernel 페이지가 숨겨지거나 터미널 조작을 중지하면 출력도 멈춘다. 다시 돌아오면 남은 글자부터 이어서 출력한다.
출력 종료 시 입력창을 자동 선택하지 않는다. 한글·이모지·결합 문자는 문자 단위로 출력한다.
Pause World가 켜진 대화는 진행 중 게임 시계를 멈춘다. 초기 안내는 메일을 읽은 뒤 Kernel로 돌아오기 전에도
시계를 멈춰 첫 예약 손님이 설명 도중 들어오지 않게 한다. 안내 종료 뒤 기존 예약과 Thread 처리가 이어진다.

지시와 다른 유효한 명령은 실제 실행하고 다음 단계로 넘기지 않는다. 처음 두 번은 Forgiving Replies를,
세 번째부터 Angry Replies를 사용한다(Angry After로 변경 가능). 오타·실패한 명령과 도움말 요청은 세지 않는다.
화를 내는 횟수는 Kernel 의심도와 별개다. 이 대화 때문에 의심도나 사건 결과가 임의로 변하지 않는다.
어떤 Lines에도 Emotion=Angry를 지정할 수 있다. Effect Seconds 동안 CRT 화면에만 붉은 신호와 빠른 동기 흔들림,
지나가는 노이즈를 적용한다. CrtScreen의 Conversation Jitter / Conversation Noise에서 강도를 조정한다.
카메라·모니터 본체는 흔들지 않는다. 메뉴·다른 페이지에서는 신호 효과를 끄고 기본 스캔라인으로 돌아간다.

기본 안내는 도움말 → 빈 치환문 등록 → 지휘소 연결 → 통신 확인 → 치환문 해제로 진행한다.
지휘소나 새 세계 객체를 만들거나 지우는 연습이 아니다. 커피 요청은 종료 안내에서 다음 사용 예로 소개한다.
대사 번역은 KernelOnboardingTexts.asset의 키로 관리하며 기존 Text Table / Excel Translations를 사용한다.
On Complete와 각 단계의 On Complete는 공통 트리거·퀘스트 결과를 설정한다.

단계, 현재 출력 위치, 지시 외 행동 횟수, 연습 이름, 대사 기록을 저장한다. 수동·빠른 저장으로 출력 도중에도
